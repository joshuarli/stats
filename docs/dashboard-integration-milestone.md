## Investigation journeys

- **Return to a list.** A host investigation now returns to the same search, status filters, sort, and page. Projects previously had no filter; users can now search name, ID, or Worker and return to the same filter and sort after investigation. Filtering does not refetch project data, and an expanded chart unmounts while its row is hidden. Browser Back restores focus to the selected row when it is still present; choosing the global navigation keeps focus on that control. This state lasts for the current dashboard session. A metric sort now reports that it is loading the full matching fleet, aborts obsolete or remaining requests on a sort change or failure, and reports a failed sort instead of silently showing an unqualified order. It loads all matching histories for ordering but requests system details only for hosts that appear on a visible page. Desktop and mobile tests cover cancellation, failure, retry, and ordering across pages. The [desktop](dashboard-integration/project-search-desktop.webp), [tablet](dashboard-integration/project-search-tablet.webp), and [mobile](dashboard-integration/project-search-mobile.webp) captures were reviewed; mobile keeps the full comparison basis readable and signals when the table can scroll.
- **Issues and traces.** An explicit project section survives reload and browser history. Explicit telemetry ranges and deployment links now survive same-page navigation; browser history also restores the default range. The selected issue remains available after the trace closes. Selecting another trace or issue aborts the previous detail request; leaving Requests aborts deferred exploration before it can fetch traces. Resolving an issue aborts the previous modal occurrence request. Resolve and reopen report pending, acknowledged success, or failure, and focus moves to the feedback when a selected issue disappears. The [mobile trace before](dashboard-integration/trace-before-mobile.webp) clipped invocation facts and stack frames. The [mobile trace after](dashboard-integration/trace-after-mobile.webp) keeps them within the visible timeline while the timeline can scroll horizontally.
- **Cost to requests.** Ledger details show the full selected route, statement, or object method, the relevant unit, and both comparison windows. On desktop those details previously hid the context and left long identities dependent on hover; the [before](dashboard-integration/ledger-desktop-before.webp) and [after](../cloudflare/test/ui/replay.spec.ts-snapshots/stuff-1h-ledger-desktop-darwin.webp) captures show the added context. Changing the settled window cancels the old ledger requests and hides a comparison from a different window until its replacement arrives. Monthly bills are keyed by project and settled time; while a matching bill loads, the ledger says so instead of displaying an earlier bill. A failed load remains unavailable until a successful retry. The [mobile ledger capture](../cloudflare/test/ui/replay.spec.ts-snapshots/stuff-1h-ledger-mobile-darwin.webp) shows the narrow layout. Observed-project route contributors can open Requests using their complete label. If retained telemetry has no exact match, Stats says so and does not show other routes' traces as evidence. No Requests exploration is fetched until the section opens.
- **Deployment evidence.** The [service table before](dashboard-integration/service-before.webp) squeezed the operation name into one-character lines. The [service table after](../cloudflare/test/ui/services.spec.ts-snapshots/service-web-desktop-darwin.webp) keeps the name and heading on one line and wraps per-unit details within a bounded column. The focused regression also exercises a longer operation and work counter. A different deployment never displays the prior deployment’s comparison. When only the comparison window changes, the previous window stays visible with an explicit updating label. Service application-work details and the header also identify their retained previous window. Obsolete comparison and rollout-impact requests are canceled. Comparisons show exact before and after windows with their time zone, identify the excluded time between them, and explain service-source coverage without hover. A limited comparison and its application-work table no longer claim that an overlap will become ready when the after window settles. The [mobile deployment capture](../cloudflare/test/ui/observe.spec.ts-snapshots/stats-deployments-mobile-darwin.webp) keeps route identities and comparison values readable. A captured deployment test opens an associated issue and trace, returns to the issue, and restores focus to the deployment evidence. When no events support a rate or mean latency, the service comparison labels it unavailable without appending a misleading unit; a measured zero remains zero.

Stats uses the existing `ActionStatus` component for issue mutations. A Stats browser test mounts the packaged menu and select and verifies their keyboard input does not trigger global shortcuts; those shortcuts still work after the controls close. The library also fixes nested mixed-axis `SplitPane` ownership. The additive `WorkbenchDrawerControl` API lets a host control navigation and workspace drawers with `open` and `onOpenChange`. The canvas fixture exercises it without accessing dialog internals; Stats does not yet use that drawer API. The new controlled `SortableHeader` is used by the paginated fleet table and the selectable route table: only the active column exposes its sort direction, and keyboard sorting retains focus and route selection. ## Lifecycle

On the current candidate, ten Fleet-to-Host chart cycles in the default fixture left zero additional DOM nodes and listeners and zero uPlot roots after leaving the host. Forced-GC heap rose 665.5 KiB and backing storage did not change. The repaired-baseline observation was +676.7 KiB heap and −0.3 KiB backing. Both are single observations, not a retained-memory trend. Host and project history revalidations returned 304 with no response body for 1h, 24h, and 7d ranges.

The large fixture contains 24 hosts and 12 projects. Request-only runs, refreshed at `7e374ca`, found identical cold API counts on every route. The candidate reported the expected unavailable `usr-memories` deployment histories and `web` issue collection. Errors adds one CSS request, as in the default fixture. Projects made 50 total requests, including 38 API requests; Fleet made 27, including 21 API requests. Sorting Fleet by CPU loaded all 24 distinct histories and produced the same ascending values across all three pages on both versions. On the captured fixture, the first sorted page used 39 API requests instead of 49: system lookups fell from 24 to 14, and JSON bytes from 10,428 to 7,626. Four newly visible hosts account for the lookups beyond the original ten. After opening all three pages, both versions had made 49 API requests. Neither run recorded a failed request; these are request counts, not timing measurements.

Five alternating baseline–candidate pairs then measured from clicking CPU sort until the first globally sorted page and its requests settled. History responses were served directly through Chromium's 150 ms latency and 1.6 Mbit/s emulation, using the large captured fixture and Node 26.13.0. The median was 5,765.3 ms (range 5,755.8–5,780.1) before and 5,683.1 ms (5,680.0–5,686.4) after: 82.2 ms less, or 1.4%. All ten runs passed the load checks before and after, loaded 24 distinct histories, produced the same order across all pages, and recorded no failed requests. Task-time differences were within the observed spread. This is a preview-fixture result; it does not establish the same gain on another network or fleet. `--fleet-sort-only` in the browser benchmark preserves this measurement boundary for future comparisons.

The `7e374ca` candidate's 100-navigation retention run exercised all three Fleet pages. After forced collection, it grew from 5,585.4 to 29,425.0 KiB of JavaScript heap and from 1,226.1 to 16,595.8 KiB of backing storage. Its checkpoints after step 25 contained 4,808–6,068 DOM nodes and 218–242 listeners. The final Fleet view retained no uPlot roots. The baseline grew from 5,534.1 to 29,117.2 KiB of heap and from 1,208.5 to 16,621.2 KiB of backing storage, with 4,566–5,823 nodes and 217–241 listeners after step 25. These are single observations, not a leak-rate or timing comparison. The benchmark now navigates to the intended page even when the fleet retains its previous page and preserves the selected range between routes.

The original large run repeatedly waited five seconds for failed responses whose bodies the frontend had not canceled. Stats now cancels unread error bodies while preserving their reported status and message. The default and large request comparisons remeasure the baseline with the same cleanup so those responses are counted on both sides.
